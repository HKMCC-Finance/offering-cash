03

Checks — scan order

15 min

Before feeding anything into the scanner, write down the check numbers in the order you feed them. That handwritten list is the ground truth for this test.

python src/check_scan.py --img_dir <scan folder> --report_file <report.xlsx>

The report rows should match your handwritten list top to bottom. If they don't, the scanner isn't stamping file times in scan order — try the alternatives and tell me which one matches:

python src/check_scan.py ... --order filename
python src/check_scan.py ... --order checknum
Partly answered already (2026-08-22)

Production scans live beside each report, in E:\헌금보고서\<date>\헌금보고서_<date>_<mass>미사_checks\. The real filename format is <account>_<check#>.Front.tif (e.g. 1010143133072_0308.Front.tif) — note the dot before Front, not the underscore the examples assume. parse_check_number() handles it; all 17 files in the sample folder parsed correctly.

File times are sequential within a scanning session (6–12 s apart, consistent with sheets going through the feeder), so --order scan — the default — is well founded. And scan order genuinely differs from filename order, confirming the original complaint: on the sample folder the two disagreed almost completely.

A scan folder can hold more than one Sunday

헌금보고서_08-09-2026_11시미사_checks holds 17 scans: 8 written 2026-08-09 12:44–12:45 and 9 written 2026-08-16 12:44–12:45 — a whole second week scanned into the previous week's folder. Every other folder checked held exactly one date, so this is a workflow slip rather than the norm, but check_scan.py will happily write all 17 rows into the one report. Check the folder's file dates before running it.

04

Checks — accuracy baseline

30 min

This is the step that turns "roughly 30% wrong" into something measurable. Use a real batch — 100 checks if you have them, 20 if you don't.

After the run, open the review sheet written next to the report (<report>_검토.xlsx). It lists every check with the raw OCR text, both amount reads, and why each row was flagged.

Building the truth file

Go down the review sheet and correct the 발행자 and 금액 columns by eye. Then save it as truth.csv with just three columns, renamed:

filename,name,amount
DEP_1043_Front.tif,John Smith,125.00
DEP_207_Front.tif,Mary Kim,20.00

That file is the durable asset here — every future model comparison runs against it:

python src/benchmark_ocr.py --img_dir <scans> --truth truth.csv --backend legacy
Check first

If amount accuracy comes back near zero, the region boxes in src/check_rois.json are cropping the wrong part of your scans. Open one .tif, note roughly where the $ box and the written-amount line fall as a fraction of the image, and send me the numbers — those defaults are standard-layout estimates, not measured from your scanner.

05

수표정리 summary and printing

10 min
Do not use --summary-anchor

Direct inspection of E:\헌금보고서\헌금보고서_양식.xlsx (rows 19–29) found it already has a working 수표정리 block: 11 predefined amount rows — $5/10/15/20/25/30/45/50/100/200/600, not the $5/10/20/25/50/100 that check_summary.py assumes — that auto-tally via COUNTIF($L$4:$L$30, ...) formulas. Those fire on their own once check amounts land in column L. --summary-anchor would overwrite them with Python-computed values using the wrong list.

Just run:

python src/check_scan.py --img_dir <scans> --report_file <report.xlsx> --print-layout

Measured on the 2026-08-22 17시 report before the volunteers' test:

The two-page split is deliberate: the template carries a manual column break after column H, so page 1 is the cash/check summary (B–H) and page 2 is the check listing (I–L). Row heights are left alone — at 0.25" margins the rows already fill the height, so the gain comes from the margins and from replacing the fixed 68% scale.
